# 洛谷

## 算法知识地图 { #algorithm-map }

拿到一道题，先判断**要求什么、输入有什么性质**，再选算法。下面是本专栏已有内容的阅读线索，不是一套覆盖所有题目的自动判题规则。

=== "范围与顺序"

    ```mermaid
    flowchart TD
        Q[先看数据性质] --> A[有序或有单调性]
        Q --> B[需要重排元素]
        A --> C[二分查找]
        B --> D[排序]
    ```

=== "状态与转移"

    ```mermaid
    flowchart TD
        Q[再看状态关系] --> A[从已知状态推导]
        Q --> B[枚举并撤销选择]
        A --> C[递推]
        B --> D[回溯]
    ```

=== "图与路径"

    这一支只讨论无权图或非负权图；有负边时需要另选最短路算法。

    ```mermaid
    flowchart TD
        Q{要求最短路吗} -->|否：遍历或连通| T[BFS / DFS]
        Q -->|是| W{无权或各边等权吗}
        W -->|是| B[BFS]
        W -->|否：边权非负| D[Dijkstra]
    ```

!!! tip "先分清：最少几步，还是最小总代价？"
    如果每条边代价相同，BFS 的层数就对应最少步数；如果边权不同但都非负，就要比较累计距离，可以考虑 Dijkstra。DFS 能找出一条可行路径，但通常不能保证第一次找到的就是最短路径。

    因为算法题基本上都是单一模块的逻辑实现，根本用不到 VS 里那些复杂的项目管理功能。强行用 VS2022 反而觉得很拖沓，体验上可能还不如轻装上阵的 VS Code。为了写个简单的算法去启动那么庞大的软件，实在有点‘杀鸡用牛刀’。

    我觉得写代码也讲究一种‘极简主义’：如果只是算个 1+1，我们在纸上写就好，何必非要开台高配电脑去跑呢？

    其实现在的人工智能发展也是这个道理。大家都觉得 Gemini、ChatGPT 这种大模型很牛，但模型真的不是越大越好。在实际应用里，如果一个专精且轻便的小模型就能完美解决当前的需求，我们完全没必要盲目追求那种‘高大全’的模型。做减法，有时候反而更高效。”
